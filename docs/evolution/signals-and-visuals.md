# Живые сигналы и графика

Статус: предлагаемый дизайн. Частоты/TTL ниже — стартовые настройки DEV/OS,
не гарантии стороннего API. API-возможности проверены 31 октября 2026.

## 1. Новые визуалы

| Визуал | Как выглядит | Как строится | На что может реагировать |
| --- | --- | --- | --- |
| **Gravity Well** | Чёрное ядро, аккреционный диск, световые дуги, падающие частицы | Кешированная 3D-точечная орбита, depth buffer, художественное искривление проекции | Размер очереди → плотность диска; завершение задачи → выброс |
| **Torus Knot** | Плотный светящийся узел с затенённой трубкой | Параметрический узел p=2/q=3, кольцевые сечения, LOD под число клеток | Активные задачи → число трассеров; результат теста → фронт по узлу |
| **Packet Garden** | Из событий растут ветви, затем медленно гаснут | Ограниченный граф ветвей с seed; фиксированный максимум узлов | Тип события задаёт форму/цвет, arrival rate задаёт рост |
| **Twin Core** | Два реактора и мост с пакетами между ними | Две оболочки + траектории Bezier, очередь отображается отдельными спутниками | Agent handoff и статусы выполнения |
| **Voxel Tide** | Волна из столбиков/проволочный рельеф, бегущая перспектива | Поле высот с кешированной сеткой, без тяжёлой физики | История запросов, CPU или подписанный demo-field |
| **Asset Orrery** | Механическая модель мира: ассеты и версии на устойчивых орбитах | Граф сущностей + стабильная раскладка по ID | Создание ревизии, rendition и approval; источник у каждой сущности |

Рендереры принимают параметры, а не знают про GA4, Bluetooth или Codex.
Каждый визуал имеет приятное самостоятельное idle-поведение, явный DEMO-режим,
минимальный размер и ограничение частиц. Существующие reactor/avatar/tesseract
остаются в каталоге и получают те же параметры/источники.

### Спецификация Gravity Well для первого релиза

- Три слоя: дальний диск, тёмное ядро, ближний диск с трассерами. Нужен честный
  depth/occlusion, чтобы дуги воспринимались объёмными.
- Перспектива и terminal cell aspect учитываются одинаково с текущей графикой.
- Изменение размера не пересоздаёт случайный мир: seed и возраст частиц сохраняются.
- От 400 до примерно 2000 образцов по размеру панели; точный лимит выбирается замером.
- Интенсивность света задаёт ASCII-символ и тон, фон остаётся родным чёрным.
- Линзоподобные дуги — стилизация, не научная модель чёрной дыры.
- `event burst` — конечный выброс на 1.2 секунды; очереди эффектов ограничены.
- Приёмка: читается на 28×10, выглядит объёмно на 64×24, не режется при вращении;
  pure renderer детерминирован и не выполняет I/O.

### Спецификация Packet Garden для первого релиза

- Узлы имеют тип, timestamp, parent и детерминированный угол ветвления.
- Четыре формы событий: arrival — зерно/точка, test — ветвь с сегментами,
  handoff — мост, failure — оборванная ветка с подписью в event tape.
- Старые ветви гаснут за заданное время; общий максимум 256 узлов, затем
  агрегация по типу/секунде с видимой подписью количества событий.
- У пользователя есть `calm/cinematic/showcase` и pause visual. Нельзя
  останавливать настоящий provider вслед за движением веток.
- Приёмка: 1000 событий не раздувают память, одинаковый seed и поток дают
  одинаковую топологию, важный failure не исчезает из журнала из-за LOD.

### Качество отрисовки

ASCII остаётся baseline. Опциональный Braille renderer использует сетку
2×4 подточек на символ для плавных окружностей и волн; включается отдельно
после проверки совместимости терминала. Fallback автоматический/ручной.
Sixel/Kitty graphics и загрузка видеотекстур — отдельное будущее расширение,
не обязательный backend следующего релиза.

Визуальные эффекты живут ограниченное время. Сглаживаются движение и свет;
данные ошибок, величины counters и результаты проверки не искажаются ради эффектности.

## 2. Сигналы и их смысл

| Ключ | Единица/тип | Определение |
| --- | --- | --- |
| `site.active_sessions_60s` | sessions | Различные анонимные сессии с принятым heartbeat за 60 секунд |
| `site.authenticated_online` | users | Различные авторизованные users по определённому presence-контракту backend |
| `site.active_users_30m` | users | Rolling window показателя аналитики, не мгновенное присутствие |
| `site.pageviews_per_min` | views/min | Принятые page-view events за минутное окно |
| `site.requests_per_sec` | requests/s | HTTP-запросы сервера; это не количество людей |
| `git.changed_files` | files | Реальный статус tracked/untracked с заранее заданным фильтром |
| `task.test.completed` | event | Результат действительно запущенной команды с run ID и exit code |
| `body.heart_rate` | bpm | Последний измеренный BPM от выбранного устройства/bridge |
| `body.rr_interval` | ms | Измеренный интервал, если он предоставлен устройством |
| `agent.handoff.ready` | event | Завершённое валидное сообщение, которое можно передать |
| `demo.build.finished` | event | Полностью синтетическое событие сцены кода |

Отсутствие образца — `null`, не 0. Нельзя переименовать requests/s в visitors
ради удобной шкалы. Окна, единицы и источник входят в описание метрики.

## 3. Набор источников

| Provider | Что даёт | Первый шаг | Внешние требования |
| --- | --- | --- | --- |
| `demo` | Детерминированный сценарий и gauges | Сразу | Нет |
| `json-stream` | Нормализованный JSONL через stdin/собственный pipe | Первый data milestone | Утилита, которая пишет по контракту |
| `json-file` | Последний атомарно обновлённый snapshot | Первый data milestone | Локальный файл, read-only со стороны DEV/OS |
| `http-json` | Aggregated metrics с выбранного endpoint | Сайт | URL и optional env token |
| `git` | Дерево и status локального workspace | Локальная работа | Git; parser использует machine-readable output |
| `task-runner` | Начало/итог разрешённой команды и её артефакты | Локальная работа | Явно выбранная команда, cwd и политика запуска |
| `ga4` | Активность в rolling window | Дополнительный адаптер | Настроенная property, доступ к Data API |
| `heart-rate-bridge` | BPM и optional RR | Личный сигнал | Совместимое устройство и bridge |
| `agent-*` | Структурированные сообщения/статусы | Arena managed | Поддерживаемый CLI/SDK и доступ пользователя |
| `replay` | Записанные события | Recorder milestone | Локальная запись, без сети |

Первым универсальным live-адаптером стоит сделать JSON file/stream, затем HTTP.
Так к пульту можно подключить собственную статистику, домашние датчики, счётчик
пользователей игры и другие источники без новых зависимостей в ядре.

Чтение произвольного файла как live-source — отдельная настройка пользователя;
это не расширение текущего allowlist чтения кода Ekza.

## 4. Посещения сайта

Сайт и текущий analytics stack пока не выбраны. Контракт позволяет подключить
существующий endpoint; реализация такого endpoint на сайте — отдельная задача.
DEV/OS в первом live milestone получает только агрегаты через read-only HTTP.

Предлагаемый ответ endpoint:

```json
{
  "schema_version": 1,
  "observed_at": "2026-10-31T12:00:00Z",
  "active_sessions": 28,
  "active_window_seconds": 60,
  "pageviews_per_minute": 84,
  "pages": [{"path": "/ekza", "active_sessions": 12}],
  "collection_status": "ok"
}
```

`pages` может быть неполным top-N, поэтому его сумма не обязана равняться
общему online. Ссылка на endpoint задаётся конфигурацией; токен — ссылкой на env.
Poll: стартово 5 секунд, stale после 15, unavailable после 60. Значения
подстраиваются под лимиты поставщика.

`observed_at` означает время измерения в upstream, а не время выдачи кеша.
Повторный ответ с тем же timestamp/measurement ID не делает sample свежим:
отдельно обновляется только состояние HTTP-соединения. Политика возраста
описана в [architecture.md](architecture.md#5-происхождение-и-качество-данных).

Если своего online нет: будущий collector принимает heartbeat активной страницы
примерно каждые 15 секунд, дедуплицирует вкладки/сессии и считает TTL 60 секунд.
Это **active sessions**, не доказанное число людей: блокировщики, невидимые
страницы и throttling влияют на наблюдаемость. Авторизованный presence backend
может отдельно считать users; определение и окно остаются видны.

GA4 Realtime показывает данные за последние 30 минут, для Analytics 360 — до
60 минут. Его `activeUsers` следует отображать с этим окном. Это документированная
альтернатива, а не обещание мгновенного online.
[Google Analytics Realtime](https://developers.google.com/analytics/devguides/reporting/data/v1/realtime-basics).

Начальная визуализация агрегатная: кластеры страниц и интенсивность событий.
При ограничении в 200 частиц подпись сообщает масштаб. Точные session paths
не синтезируются из агрегатных счётчиков. Raw IP, email и идентификаторы
пользователей для такой сцены не нужны.

## 5. Настоящий пульс

Первая portable-интеграция — локальный bridge, отдающий JSON:

```json
{
  "schema_version": 1,
  "source": "heart-rate-bridge",
  "received_at": "2026-10-31T12:00:00Z",
  "heart_rate_bpm": 72,
  "rr_intervals_ms": [830, 836],
  "sensor_contact": "good",
  "timing_basis": "notification_received"
}
```

Стандарт Bluetooth Heart Rate Service передаёт heart-rate measurement через
notifications; RR-поля optional, аппаратного timestamp измерения этот сервис
не предоставляет. Сервис/характеристика имеют UUID `0x180D` / `0x2A37`.
[Bluetooth HRS](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/HRS_v1.0/out/en/index-en.html),
[Assigned Numbers](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Assigned_Numbers/out/en/index-en.html).

Следствия для дизайна: BPM можно показывать числом и задавать им частоту
художественной пульсации. Наличие BPM не даёт измеренную форму ЭКГ. RR можно
показывать точками/интервалами, сохраняя качество их временной привязки.
Не следует интерпретировать время получения батча RR как точные timestamps ударов.

BLE-адаптер и его пакет — опциональная интеграция после выбора оборудования.
Часы с закрытым API могут потребовать телефонный bridge; наличие Bluetooth
у часов само по себе не означает поддержку стандартного HRS. Прямой доступ
из Python к любым часам не обещается.

Стартовые состояния: fresh до 3 секунд, затем stale; после 10 секунд без
образца число `--`, рисунок `NO SIGNAL`. Частота обновления зависит от устройства.
Личный поток локален по умолчанию; в Stream View скрыт, в запись/экспорт
попадает только при выборе этой категории.

## 6. Готовые bindings

| Сигнал | Параметр | Преобразование | Если сигнала нет |
| --- | --- | --- | --- |
| active sessions | particle count | log1p, 0…200, EMA 0.8s | Fade, `UNAVAILABLE` |
| requests/s | disk flow speed | linear clamp, 0.2…2.0 | Neutral idle, без поддельных rps |
| agent queue length | satellites | Один спутник/задание до 12, затем group count | 0 только при подтверждённой пустой очереди |
| handoff.ready | packet transfer | Конечный эффект по message ID | Эффект не запускается |
| test results | shield segments | На run ID, pending/pass/fail | Показать unknown, не зелёный success |
| git changed files | aurora sources | Изменения относительно предыдущего sample | Сохранить историю, убрать LIVE-подсветку |
| BPM | core pulse period | 60/BPM; визуальное сглаживание | `NO SIGNAL`, neutral idle |
| RR interval | scatter position | Реальные ms, без синтеза промежуточных точек | Скрыть scatter |

К числам графического binding можно применять сглаживание. Значения карточек
не подменяются параметрами картинки. Для пороговых эффектов используется
hysteresis/cooldown, чтобы колебания около границы не создавали мигание.

## 7. Режиссёр событий

В `spectator` режиме очередь cues выбирает сцену: handoff → Twin Core,
всплеск активности → Audience Orbit, бездействие → спокойный Gravity Well.
Приоритеты: запрос пользователя > важное событие > декоративная автосмена.
Cooldown переключения — стартово 10 секунд. Несколько одинаковых событий
объединяются в один эффект с подписью `×N`.

Пока пользователь печатает в терминале, режиссёр может изменить свет/эффект
существующего визуала, но не экран, размер PTY, выбранную панель и фокус.

## 8. Что добавлять после основного набора

Local CPU/memory/temperature, аудиоспектр выбранного аудиоисточника, игровые
сессии OMOBA, очередь рендера/обработки ассетов, домашние датчики и GitHub/GitLab
события. Каждый источник проходит тот же контракт: значение, единица, окно,
timestamp, mode, quality. Если возможен только периодический REST-опрос,
интерфейс не изображает его как непрерывный поток измерений.

Следующие проверки выполняются при реализации: потеря сигнала, malformed JSON,
задержка и дубликаты, ошибка авторизации, квота, overflow, bounded memory,
отсутствие утечек персональных данных в scene capsule и запись replay.
